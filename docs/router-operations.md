# Проверенные сведения для эксплуатации

Актуальность: 8 сентября 2026 года; дополнено 27 сентября. Это наблюдения на действующем роутере;
после обновления системы проверяй только те свойства, на которые влияет изменение.
Адреса устройств и SSH alias находятся в локальном файле вне Git.

## Система и команды

- Активный движок: sing-box **1.13.11**, linux/arm64, Go 1.25.9;
  `/usr/local/bin/sing-box`, служба `/etc/init.d/sing-box-router`.
- Конфигурация: `/etc/sing-box-router/config.json`;
  постоянное состояние: `/var/lib/sing-box-router`, включая `cache.db` с fake-IP.
- Служба читает весь каталог конфигурации через `-C`. Кандидаты и резервные
  копии `.json` храни вне этого каталога; для атомарной замены используй в нём
  скрытый файл `.next` без расширения `.json`.
- TrustTunnel работает отдельным процессом `trusttunnel_client`. Порты loopback:
  10809 — SOCKS с политикой sing-box, 11080 — прямой SOCKS TrustTunnel,
  9090 — Clash API. Не выводи содержимое закрытых конфигураций.
- Проверены доступными: `sh`, `curl`, `sha256sum`, `awk`, `sed`, `nslookup`,
  `cmp`, `ls`, `cp`, `jsonfilter`.
- **Отсутствуют** `nohup`, `stat`, `unshare`, `nsenter` и
  `/usr/libexec/sftp-server`. Не рассчитывай на GNU/Linux набор инструментов.
- Для проверки сохранения inode используй `ls -di PATH | awk '{print $1}'`.
  Для сохранения прав: `cp -p ACTIVE NEXT`, затем запиши кандидата в `NEXT`.
- `jsonfilter` возвращает код 1 при отсутствии необязательного `clash_api.secret`.
  Проверяй оба случая явно: 27.09.2026 необработанный код при `set -e` вызвал
  ложный откат проверки; тест исправлен для присутствующего и отсутствующего поля.
- Проверенный независимый запуск: `sh -c 'trap "" HUP; SCRIPT' >LOG 2>&1
  </dev/null &`. SCRIPT обязан сохранять итоговый статус и откатывать конфигурацию
  при любой ошибке после переключения. Родительская команда не доказывает успех.
- `codex-ssh-mux copy-to` требует отсутствующий SFTP server и здесь завершается
  ошибкой. Не повторяй и не обходи mux прямым scp. Для узкой текстовой правки
  проверено преобразование копии конфигурации через `run` с последующей сверкой
  SHA-256 с локально проверенным кандидатом. Полноценная загрузка требует отдельно
  подготовленного рабочего способа, а не установки пакета по умолчанию.

Для SSH из домашней LAN сначала используй проверенный локальный адрес из
закрытых заметок. Проверяй `ssh -G`: оставшийся ProxyCommand старого прокси-клиента
может оборвать соединение до аутентификации, даже когда роутер доступен напрямую.
Не запускай прежний прокси-клиент автоматически; используй текущий сетевой путь.

## Что не работает как горячее обновление

Проверено по исходникам sing-box 1.13.11 и доступному API:

- `GET /providers/rules` возвращает заглушку `{"providers":[]}`;
  именованный provider возвращает 404.
- `PUT /configs` возвращает 204, но конфигурацию не применяет.
  `PATCH /configs` меняет режим; это не перезагрузка конфигурации.
- SIGHUP проверяет конфигурацию, затем закрывает и пересоздаёт весь экземпляр:
  TUN, слушатели и активные соединения. Он **прерывает трафик** и не гарантирует
  свежую загрузку удалённых списков. 27.09.2026 на sing-box 1.13.11 он завершился
  FATAL `TUNSETIFF: device or resource busy` и откатом. Не считай HUP безопасным:
  проверенный порядок — штатный `stop`, ожидание завершения прежнего PID, `start`;
  завершение процесса освобождает TUN.
- У удалённых списков штатный `update_interval: "2h"`. Не обещай немедленное
  применение одной только публикацией списка. Полный refresh из README обновляет
  все списки, останавливает сервис и перезапускает dnsmasq. 27.09.2026 SHA-256
  скрипта на устройстве совпал с репозиторием; для добавления одного CBS он не нужен.

## Kinopub: причина и исправление

При буферизации Apple TV обращения к `proxykp.xyz` уходили direct, с нулевым
скачиванием. Прямой доступ к двум IPv4-адресам завершался таймаутом. Через
TrustTunnel с фиксированным IPv4 и сохранённым TLS SNI получен HTTP 200 примерно
за 0,5 секунды; SOCKS-запрос с доменным именем завершался таймаутом за 12 секунд.
Это измерение конкретного эпизода, не обещание постоянной доступности CDN.

Исправление в шаблоне после DNS hijack: сначала `action: resolve` для
`proxykp.xyz` через `dns-direct` с `strategy: ipv4_only`, затем `outbound: tt-t`
для `proxykp.xyz` и `sgupd.com`, включая поддомены. Одного добавления mirror
в список T недостаточно для наблюдавшегося таймаута SOCKS по имени.
Не направляй весь трафик Apple TV в T ради исправления одного сервиса.

`resolve` действует на доменный destination. При настоящем IP и домене из sniff
исходный адрес сохраняется; `ipv4_only` не превращает такой IPv6-адрес в IPv4.

Локальная проверка той же версии sing-box: 21/21 сценарий, компиляция шести
исходных списков, обе проверки конфигурации. Покрыты apex/subdomain, fake-IP,
literal IP + sniff, IPv4 SOCKS, сохранение Host/SNI и неизменность посторонних
маршрутов. Fixture работает без TUN; это не проверка реальной линии или фильма.
Внешние geosite в fixture заменялись заглушками.

17.09.2026 при неисправном начальном экране Kinopub наблюдались обращения к
`1abab.ru` и `api.boramoraboom.ru` по direct. Оба точных домена и их поддомены
добавлены в T, включая явное правило роутера для применения без ожидания
обновления списков. Обычные HTTPS-запросы к корням обоих сайтов отвечали и напрямую,
и через T с доменным назначением; отдельный `resolve` для них не требуется.
Эти запросы не проверяют работу интерфейса или воспроизведения видео.

## Минимальный порядок применения

1. Проверить master и возможности команд; снять только необходимые конфигурацию,
   версии и агрегаты. Кандидата собрать и проверить локально той же версией.
2. Выполнить проверки, подписать и опубликовать изменения. Сохранить неизменяемый
   артефакт, checksum и предыдущую версию. Если новая запись в общем списке
   требует новой логики роутера, публиковать этот список после включения логики.
3. Подготовить копию кандидата на роутере, сверить checksum и выполнить
   `/usr/local/bin/sing-box -D /var/lib/sing-box-router -c CANDIDATE check`.
   `check` не запускает сервис. Не запускай второй TUN и не открывай рабочий cache
   параллельным экземпляром. Средств для изолированного netns сейчас нет.
4. Проверить свежую активность по счётчикам `/connections`: короткое окно,
   объём полезного трафика и новые попытки воспроизведения, исключая DNS, время,
   push и Tailscale. Выводить только итог и время, без адресов/строк соединений.
   При активности отложить переключение; после команды на продолжение повторить
   gate и штатно переключать при тишине. Отсутствие данных не равно тишине.
5. Перед переключением сохранить проверенную конфигурацию в отдельный каталог
   `/root/router-stack-backups/`, PID TrustTunnel, inode каталога/cache и известное
   fake-IP соответствие. Повторить gate. Не удалять и не заменять `cache.db`.
6. Подготовить скрытый `.next` в каталоге конфигурации с сохранением прав.
   Выполнить `/etc/init.d/sing-box-router stop` и дождаться завершения прежнего PID;
   до его завершения не запускать новый экземпляр. Атомарно заменить конфигурацию
   файлом `.next`, затем выполнить `/etc/init.d/sing-box-router start`.
   При ошибке восстановить исходный конфиг с тем же порядком stop → выход PID → start.
7. Проверить HTTPS к `proxykp.xyz` через policy SOCKS 10809, контрольный HTTPS,
   сохранение fake-IP, inode и PID TrustTunnel. Не перезапускать TrustTunnel,
   dnsmasq, Tailscale или весь stack ради этой правки. Хранить проверенный backup.

Выкладка 08.09.2026 прошла эти проверки за 12 секунд после сигнала; это время
до успешного health-check, не измеренный downtime. Проверка фильма отдельно
требует активного воспроизведения.

27.09.2026 после двух описанных выше откатов добавлен список
[CBS / Paramount+](https://raw.githubusercontent.com/SagerNet/sing-geosite/rule-set/geosite-cbs.srs)
в существующую группу A. Штатный stop/start прошёл проверку через 5 секунд:
Paramount+ — HTTP 302, контроль T и Kinopub — HTTP 200. Сохранены inode каталога
и cache, fake-IP, процессы TrustTunnel и dnsmasq. Эти 5 секунд — время до проверки,
не измеренный downtime; HTTP-ответы не подтверждают воспроизведение фильма.

Скрипт refresh-sing-box-rules.sh принимает имена remote rule-set:
например, /root/bin/refresh-sing-box-rules.sh manual-a. Без аргументов обновляет все.
Неизвестные теги отклоняются до остановки служб. Перед копированием cache
и запуском временного экземпляра скрипт должен дождаться завершения прежнего
управляемого процесса; возвращение команды stop само по себе этого не доказывает.

Это не горячая перезагрузка: скрипт сохраняет cache, запускает временный
экземпляр для выбранного ресурса, затем возвращает штатный сервис и перезапускает
dnsmasq. Перед выполнением обязательны gate, backup и предусмотренные проверки.
Новая версия установлена; проверка и откат описаны в журнале ниже.

Успешный native API выводит `State: started`, Tailscale — `State: Running`. Каталог `/etc/sooslique/trial` сохраняется после завершённой миграции: его наличие не означает активную транзакцию. Для этого устройства проверен строго read-only `sh /etc/sooslique/switch.sh permit-tailnet-capture` (confirmed + retired); gate повторяется под EX-lock. DNS smoke использует `nslookup -type=A www.google.com 127.0.0.1` и требует exit 0: частичный A при ошибке AAAA нельзя считать успешной полной проверкой.


## 04.11.2026 — приоритет T и передача команд SSH

На OpenWrt 25.12.5 две передачи shell-скрипта через аргумент SSH длиной 40 352 байта оборвали соединение до исполнения. В журнале Dropbear подтверждены два `bad packet size`, последний — 40 396 байт. После восстановления оставались прежние config checksum и PID. Для больших проверенных скриптов использовать короткую команду `codex-ssh-mux run TARGET "sh -s"` с точными байтами скрипта на stdin; вложенные команды не должны потреблять этот stdin. Не повторять длинный `sh -c` и не создавать новый master без разрешения владельца.

По явному разрешению владельца в группе T изменён только порядок fallback: `TR-2 → TR-1 → TR-3` на `TR-1 → TR-2 → TR-3`. Источник операции — подписанный commit `c504aa9f0c7b19922873318858c4e2e6385e2e63`, тег `router-t-priority-20261104-r2`. SHA-256 неизменяемого комплекта операции: `366371d8f1794b7d2e8b346a49fa52fef655eaf38249e853f4ad5dd8fb9d1fe9`. Пакеты, бинарники, скрипты и службы не устанавливались и не обновлялись; ядро осталось `29cef2bd`.

Нативный PutConfig дважды отказал до записи: legacy-правка не воспроизводится без потерь в сохранённом portable profile. Защита не ослаблялась. Проверенная замена выполнена через SSH под штатным EX-lock: config check, stop, выход прежнего PID, атомарный rename соседнего скрытого файла, start и health; предусмотрен автоматический config-only rollback. До изменения проверены свежий архив и его копия вне устройства. Исходный config SHA-256: `9a983f107e0b23d86d036960d64bb55ac952b0d851dc040a8f5aeee4c0fb9907`; активный: `0ce5702681ba04338a7e755163e155229ccfc5ca58d068de9fd562d0f6049a09`. Backup SHA-256: `8bc15accc6dd1909ad70d9bcefcfbcd499c4378bef159196364e13f3e9b0529d`; закрытые привязки сохранены локально.

После запуска подтверждены TR-1, авторизованный API, Tailscale Running, DNS A и HTTPS YouTube через policy SOCKS. Время от stop до API — 4,84 с. Остались прежними бинарники, TLS/init/CLI/switch/firewall include, inode кэша и persistent directories, идентичность Tailscale, байты всех сохранённых профилей и `config.json.prev`. Native LIST подтвердил ожидаемый `externalConfig=true`, пустой effective activeID и неизменный каталог из двух профилей. Приоритет сохраняется в активном config после перезапуска; повторный выбор сохранённого профиля вернёт порядок из него. Перед sysupgrade конфигурацию включать в штатный backup и после него сверять фактический config.

Действующие DNS-guards и kill switch дополнительно проверены штатной read-only функцией `firewall_active`; проверка прошла при сохранённом `auto_redirect=false`. Первоначальное требование теста `auto_redirect=true` было ошибочным: `read_interface` допускает false, а форма активных nft-правил подтверждена независимо. За 90 секунд получено 26 полных снимков, во всех выбран TR-1. Это подтверждает стабильность выбора в данном окне; повторное открытие ленты и воспроизведение на iPhone владельцем ещё не подтверждены.

Причина выбранного изменения: в исходном порядке наблюдались повторные переходы TR-2 → TR-1 по таймаутам и возвраты на TR-2 после одной успешной проверки примерно через 15 с. По исходникам этой версии оба направления переключения прерывают соединения группы. В разных потоках одного видеохоста передача через TR-2 была медленнее, чем через TR-1; измерение не доказывает предельную пропускную способность узлов. Изменён приоритет конкретной группы, резервные TR-2/TR-3 сохранены; общий алгоритм fallback не менялся.
